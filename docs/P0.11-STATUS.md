## Result

**B4_RESEARCH_PLATFORM_EXPERT_RUNTIME_VERIFIED** (QEMU_VIRT DEV, TCG, research scope).

- `PenangQemuVirtPlatformExpert`, an `IODTPlatformExpert` subclass built into the DEV kernel, is offered to the root nub by one built-in IOKit personality (`IONameMatch "qemu,virt"`, `IOProbeScore 1000`), compiled only for the QEMU_VIRT configuration. The `IOPanicPlatform` entry is unchanged and remains the fallback.
- `probe()` re-checks the name match and requires the `qemu,virt` entry in the root `compatible` (IOKit name matching would also accept `model` or `device_type`). `start()` checks the resources it relies on before setting any platform state, then runs the generic `IOPlatformExpert::start` and registers the service.
- Positive QEMU run: selected, probe returns the instance, start returns true after the power root domain and two device-tree nubs are created, registration releases the in-kernel `cpu_boot_thread`, `IOPanicPlatform` never starts, the B4 panic is gone.
- Negative controls: an unknown platform (`compatible` replaced) is never offered to the class and ends in the original `IOPanicPlatform` panic; an identity mismatch (`model` replaced) is refused by `probe()` with `MODEL_MISMATCH` and also ends in the original panic.
- Regressions on the new kernel: P0.10 and P0.9 gate runs PASS.

## Not provided by design

NVRAM, RTC, interrupt controller, CPU power manager (`IOPMGR`), restart hardware, storage, platform UUID/serial. Nothing fictitious was created.

## Next blocker

**B5_PLATFORM_INTERRUPT_CONTROLLER** — historical P0.11 state: no panic, a quiet wait before `bsd_init`. The `cpu_boot_thread` waited in `PassthruInterruptController::waitForChildController()`; on return, the original XNU path calls `ml_set_max_cpus` **before** waiting for `IOPMGR`. Meanwhile `kernel_bootstrap_thread` waited in `ml_wait_max_cpus`. P0.12 subsequently cleared this wait in QEMU with one CPU; see [P0.12](P0.12-STATUS.md) for the current research limits.
